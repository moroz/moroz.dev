The Key-Hashed Message Authentication Code algorithm, first standardized as [RFC&nbsp;2104](https://datatracker.ietf.org/doc/html/rfc2104) all the way back in February 1997, is a cornerstone of modern cryptography.
It is widely used in software that billions of people around the world rely on in everyday life.
[TLS](https://datatracker.ietf.org/doc/html/rfc8446) uses HMAC to verify message authenticity, and, via [HKDF](https://www.rfc-editor.org/info/rfc5869/), to derive encryption keys.
[TOTP](https://www.rfc-editor.org/info/rfc6238/), or the Time-based One-Time Password algorithm, uses HMAC (traditionally with SHA-1) to generate single-use numeric codes for two-factor authentication. You may have used TOTP with Google Authenticator, Microsoft Authenticator, or similar apps.
HMAC is also the most popular authentication algorithm in [JSON Web Tokens](https://datatracker.ietf.org/doc/html/rfc7519) (JWT).

Therefore, it is with greatest regret that I admit that, until today, I have never really understood how HMAC worked.
I have used it in numerous ways, and I have even tried to read through the RFC one time, but the true meaning of all of these arcane formulae has eluded me for many years.

There is no better way to understand an algorithm than to implement it yourself, therefore in this post I'm going to implement HMAC-SHA-256 in Go.
I will not be implementing SHA-256 myself, but will use the `sha256.Sum256(data []byte)` function from the `crypto/sha256` package instead.

The general definition of HMAC, as defined in RFC 2104, is as follows:

```
H(K XOR opad, H(K XOR ipad, text))
```

In this formula, `H` represents the hash function (in our case, SHA-256) and `K` represents the secret key.

`XOR` is the bitwise _exclusive OR_ operation, which returns 1 if and only if its two operands are not equal:
