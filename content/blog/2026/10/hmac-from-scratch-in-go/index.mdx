**HMAC**, or **Keyed-Hash Message Authentication Code** algorithm, is a cornerstone of modern cryptography.
First standardized in 1997 as [RFC&nbsp;2104](https://datatracker.ietf.org/doc/html/rfc2104), it now secures software that billions of people rely on in everyday life.

To name a few examples: [TLS version 1.3](https://datatracker.ietf.org/doc/html/rfc8446) uses HMAC to authenticate handshakes, and, via [HKDF](https://www.rfc-editor.org/info/rfc5869/), to derive encryption keys.
HMAC is also widely used in **JSON Web Tokens** (JWT). In fact, HMAC with SHA-256 (`HS256`) is the only signing algorithm that a JWT implementation MUST implement, as per [RFC&nbsp;7519](https://datatracker.ietf.org/doc/html/rfc7519#section-8).

Last but not least, [TOTP](https://www.rfc-editor.org/info/rfc6238/), or the **Time-based One-Time Password** algorithm, uses HMAC (traditionally with the older [SHA-1 hash function](https://en.wikipedia.org/wiki/SHA-1)) to generate single-use numeric codes for two-factor authentication. You may have used TOTP with Google Authenticator, Microsoft Authenticator, or similar mobile apps. For an in-depth explanation of TOTP, refer to my YouTube video [Implementing 2FA Codes (TOTP) in C](https://youtu.be/TNAXkPI7JBc).

It is with deepest regret that I admit that, until today, I have never truly understood how HMAC worked.
I have used it in numerous ways, and I have even tried to read through the RFC one time, but the true meaning of all of these arcane formulae has eluded me for many years.

There is no better way to understand an algorithm than to implement it yourself, therefore in this post I'm going to implement HMAC-SHA-256 in Go.

### Formal definition

The general definition of HMAC, as stated in [RFC 2104](https://datatracker.ietf.org/doc/html/rfc2104#section-2), is as follows:

$$
\begin{aligned}
H\big( & K \xor \mathrm{opad}, \\
& H(K \xor \mathrm{ipad},\ \mathit{text}) \big)
\end{aligned}
$$

In this formula, $$H$$ represents the hash function (in our case, SHA-256) and $$K$$ represents the secret key, which is a binary string of arbitrary length. XOR refers to the bitwise _exclusive OR_ operation, and is explained in depth at a further point in this article. The symbols $$\mathrm{ipad}$$ and $$\mathrm{opad}$$ are constants. In the case of HMAC-SHA-256, $$\mathrm{ipad}$$ is the byte `0x36`, repeated 64 times; $$\mathrm{opad}$$ is the byte `0x5C`, repeated 64 times. The variable $$\mathit{text}$$ refers to the message being authenticated.

One way to break this cryptic formula into human-digestible morsels of pseudocode would be as follows:

1. $$\mathit{innerKey} \gets K_0 \xor \mathrm{ipad}$$  
   Pad the secret key $$K$$ with zeroes at the end, so that it is exactly 64 bytes long, and call the result $$K_0$$.
   If $$K$$ is longer than 64 bytes, hash the key with SHA-256 and pad the resulting hash digest rather than the original key.
   Apply the _exclusive OR_ (XOR) operation on $$K_0$$ and the constant $$\mathrm{ipad}$$ (the byte `0x36` repeated 64 times), and store the result in the variable `innerKey`.

2. $$\mathit{innerHash} \gets H(\mathit{innerKey} \,\|\, \mathit{text})$$  
   Hash `innerKey`, concatenated with the message, and store the resulting hash in the variable `innerHash`.

3. $$\mathit{outerKey} \gets K_0 \xor \mathrm{opad}$$  
   Apply the _exclusive OR_ operation on $$K_0$$ and the constant $$\mathrm{opad}$$ (the byte `0x5C` repeated 64 times), and store the result in the variable `outerKey`.

4. $$\mathit{hmac} \gets H(\mathit{outerKey} \,\|\, \mathit{innerHash})$$  
   Hash `outerKey`, concatenated with `innerHash`. The resulting binary string is the HMAC digest.

Before converting these steps into actual executable code, we need to do some prepping.

We will fix this soon by implementing the `myhmac.SHA256` function. Before we can do that, however, we need to understand the XOR operation, which is used by the HMAC key padding algorithm.

### How exclusive OR (XOR) works

XOR is the bitwise _exclusive OR_ operation. On the level of single bits, it returns 1 if and only if its two operands are not equal, and 0 otherwise. The following interactive figure displays this principle in practice:

{/* @oxfmt-ignore */}<XorTruthTable client:visible>Exclusive OR of two bits. Click to toggle the operands A and B.</XorTruthTable>

On the level of a byte, the same operation is applied to each pair of bits:

{/* @oxfmt-ignore */}<XorBytes client:visible>Bitwise XOR of two bytes. Toggle the bits of A and B, or pick a preset.</XorBytes>

XOR is widely used in cryptography as a sort of binary mask. This is due to XOR's unique reversibility:

$$
\begin{aligned}
& (A \xor B) \xor B \\
={} & A \xor (B \xor B) \\
={} & A \xor 0 \\
={} & A
\end{aligned}
$$

If you apply the same binary mask $$B$$ to the plaintext $$A$$ twice, the mask zeroes out, and you end up with the plaintext.
If $$B$$ is random and secret, <span class="text-nowrap">$$A \xor B$$</span> is as good as indistinguishable from random noise.
This property is widely used in [AEAD constructs](https://en.wikipedia.org/wiki/Authenticated_encryption#Authenticated_encryption_with_associated_data), such as [AES-GCM](https://en.wikipedia.org/wiki/Galois/Counter_Mode) and [ChaCha20-Poly1305](https://en.wikipedia.org/wiki/ChaCha20-Poly1305).

Side note: XOR is also the fastest way to zero a register in x86 assembly, because <code>xor&nbsp;eax,&nbsp;eax</code> in Intel machine code is shorter than <code>mov&nbsp;eax,&nbsp;0</code>, and because <span class="text-nowrap">$$A \xor A = 0$$</span>. On ARM processors, the idiom works as well, but since all instructions in ARM machine code have the same length, the XOR idiom has no advantage over a move.

With the XOR primer out of the way, we can proceed to pad the key.

### Padding the key

This section explains the steps necessary to calculate the inner and outer padding of the key. For both the inner and the outer padding, the steps are exactly the same, except for the constants ipad and opad that the key is combined with.

1. If the key is longer than 64 bytes, hash it with SHA-256 and use the resulting digest in place of the key.
2. Pad the key with zeroes at the end so that it is exactly 64 bytes long.
3. XOR each byte of the padded key with either the ipad or the opad constant, depending on whether you are calculating the inner or the outer padding.

Expressed in Go, the function could look like this:

```go filename="myhmac.go" imports
func padKey(key []byte, mask byte) []byte {
	buffer := make([]byte, sha256.BlockSize)

	if len(key) > sha256.BlockSize {
		hashed := sha256.Sum256(key)
		key = hashed[:]
	}

	copy(buffer, key)

	for i := range buffer {
		buffer[i] ^= mask
	}

	return buffer
}
```

Our padding function takes a key and a padding mask, and returns a byte slice:

```go unclosed
func padKey(key []byte, mask byte) []byte {
```

1. Allocate a buffer of exactly `sha256.BlockSize` bytes:

```go
buffer := make([]byte, sha256.BlockSize) // 64 bytes
```

The RFC specifies that the key should be padded with zeroes at the end. Go takes care of that by automatically filling the buffer with zeroes.
In C, you would need to allocate the buffer with [calloc(3p)](https://man7.org/linux/man-pages/man3/calloc.3p.html) rather than [malloc(3p)](https://man7.org/linux/man-pages/man3/malloc.3p.html), or call [memset(3p)](https://man7.org/linux/man-pages/man3/memset.3p.html) after allocating the buffer.

2. If the key is longer than the block size, hash it and store the digest in place of the original key:

```go
if len(key) > sha256.BlockSize {
	hashed := sha256.Sum256(key)
	key = hashed[:]
}
```

Since `sha256.Sum256` returns `[32]byte`, an array, rather than the expected byte slice, we need to convert it using the slice expression `hashed[:]`.

You might be tempted to try and inline the expression as `sha256.Sum256(key)[:]`. Alas, this does not compile: in Go, the return value of a function is not _addressable_ (it does not have a stable address in memory). To think that I chose Go over Rust because I do not care about memory safety...

3. Copy the key to the buffer. Note that the destination comes first and the source second.

```go
copy(buffer, key)
```

4. XOR each byte in the buffer with the mask value. For inner padding, it's `0x36` (`0b00110110`). For outer padding, it's `0x5C` (`0b01011100`).

```go
for i := range buffer {
	buffer[i] ^= mask
}
```

The `^=` operator is a shorthand form, inherited from C. We could also write the block body like so:

```go
buffer[i] = buffer[i] ^ mask
```

4. Return the buffer:

```go
return buffer
```
