The **Keyed-Hash Message Authentication Code** algorithm, first standardized in 1997 as [RFC&nbsp;2104](https://datatracker.ietf.org/doc/html/rfc2104), is a cornerstone of modern cryptography.
It is widely used in software that billions of people around the world rely on in everyday life.

[TLS version 1.3](https://datatracker.ietf.org/doc/html/rfc8446) uses HMAC to authenticate handshakes, and, via [HKDF](https://www.rfc-editor.org/info/rfc5869/), to derive encryption keys.
The previous version of the protocol, [TLS&nbsp;1.2](https://www.rfc-editor.org/info/rfc5246/), which is still in widespread use as of this writing, also uses HMAC for message authentication.

HMAC is also widely used in **JSON Web Tokens** (JWT). In fact, HMAC with SHA-256 (`HS256`) is the only signing algorithm that a JWT implementation MUST implement, as per [RFC&nbsp;7519](https://datatracker.ietf.org/doc/html/rfc7519#section-8).

Last but not least, [TOTP](https://www.rfc-editor.org/info/rfc6238/), or the **Time-based One-Time Password** algorithm, uses HMAC (traditionally with SHA-1) to generate single-use numeric codes for two-factor authentication. You may have used TOTP with Google Authenticator, Microsoft Authenticator, or similar mobile apps. For an in-depth explanation of TOTP, refer to my YouTube video [Implementing 2FA Codes (TOTP) in C](https://youtu.be/TNAXkPI7JBc).

Therefore, it is with greatest regret that I admit that, until today, I have never really understood how HMAC worked.
I have used it in numerous ways, and I have even tried to read through the RFC one time, but the true meaning of all of these arcane formulae has eluded me for many years.

There is no better way to understand an algorithm than to implement it yourself, therefore in this post I'm going to implement HMAC-SHA-256 in Go.
I will not be implementing SHA-256 myself, but will use the `sha256.Sum256(data []byte)` function from the `crypto/sha256` package instead.

The general definition of HMAC, as defined in RFC 2104, is as follows:

{/* @oxfmt-ignore */}<p class="text-center"><var>H</var>(<var>K</var> XOR <var>opad</var>, <var>H</var>(<var>K</var> XOR <var>ipad</var>, <var>text</var>))</p>

In this formula, <var>H</var> represents the hash function (in our case, SHA-256) and <var>K</var> represents the secret key.

We can break the HMAC calculation into the following steps:

1. Calculate the inner padding of the key <var>K</var> (explained in the next section), and store the resulting binary string in the variable `innerKey`.
2. Hash `innerKey`, concatenated with the message, and store the resulting hash in the variable `innerHash`.
3. Calculate the outer padding of the key <var>K</var>, and store the resulting binary string in the variable `outerKey`.
4. Hash `outerKey`, concatenated with `innerHash`.

6. PROFIT!!!

First, let's discuss the padding algorithm, which is arguably the most complicated part of HMAC.

### Padding the key

This section explains the steps necessary to calculate the inner and outer padding of the key. For both the inner and the outer padding, the steps are exactly the same, except for the constants <var>ipad</var> and <var>opad</var> that the key is combined with.

Our padding function takes a key and a padding mask, and returns a byte slice:

```go
func padKey(key []byte, mask byte) []byte {
```

1. Allocate a buffer of exactly `sha256.BlockSize` bytes:

```go
buffer := make([]byte, sha256.BlockSize) // 64 bytes
```

The RFC specifies that the key should be padded with zeroes at the end. Go takes care of that by automatically filling the buffer with zeroes.
In C, you would need to allocate the buffer with [calloc(3p)](https://man7.org/linux/man-pages/man3/calloc.3p.html) rather than [malloc(3p)](https://man7.org/linux/man-pages/man3/malloc.3p.html), or call [memset(3p)](https://man7.org/linux/man-pages/man3/memset.3p.html) after allocating the buffer.

2. If the key is longer than the block size, hash it and store the digest in place of the original key:

```go
if len(key) > sha256.BlockSize {
    hashed := sha256.Sum256(key)
    key = hashed[:]
}
```

Since `sha256.Sum256` returns `[32]byte`, an array, rather than the expected byte slice, we need to convert it using the slice expression `hashed[:]`.

You might be tempted to try and inline the expression as `sha256.Sum256(key)[:]`. Alas, this does not compile: in Go, the return value of a function is not _addressable_ (it does not have a stable address in memory). To think that I chose Go over Rust because I do not care about memory safety...

3. Copy the key to the buffer. Note that the destination comes first and the source second.

```go
copy(buffer, key)
```

4. `XOR` each byte in the buffer with the mask value. For inner padding, it's `0x36` (`0b00110110`). For outer padding, it's `0x5C` (`0b01011100`).

```go
for i := range buffer {
    buffer[i] ^= mask
}
```

The `^=` operator is a shorthand form, inherited from C. We could also write the block body like so:

```go
buffer[i] = buffer[i] ^ mask
```

4. Return the buffer:

```go
return buffer
```

### How exclusive OR (XOR) works

In the previous section, we have referred to the `XOR` operation. This section explains how `XOR` works.

`XOR` is the bitwise _exclusive OR_ operation. On the level of single bits, it returns 1 if and only if its two operands are not equal, and 0 otherwise:

On the level of a byte, the same operation is applied to each pair of bits:

{/* @oxfmt-ignore */}<XorBytes client:visible>Bitwise XOR of two bytes. Toggle the bits of A and B, or pick a preset.</XorBytes>

`XOR` is widely used in cryptography as a sort of binary mask. This is due to `XOR`'s unique reversibility: (<var>A</var> XOR <var>B</var>) XOR <var>B</var> always returns <var>A</var>, but if <var>B</var> is random and secret, <var>A</var> XOR <var>B</var> is as good as indistinguishable from random noise. This property is widely used in AEAD constructs, such as AES-GCM and ChaCha20-Poly1305.

Side note: `XOR` is also the fastest way to zero a register in x86 assembly, because <code>xor&nbsp;eax,&nbsp;eax</code> in Intel machine code is shorter than <code>mov&nbsp;eax,&nbsp;0</code>, and because <var>A</var>&nbsp;XOR&nbsp;<var>A</var>&nbsp;=&nbsp;0. On ARM processors, the idiom works as well, but since all instructions in ARM machine code have the same length, the `XOR` idiom has no advantage over a move.
